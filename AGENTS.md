# DiceBox Campaign Helper Implementation Contract

The authoritative project contract is this repository's `AGENTS.md`, reconciled with the current roadmap, active program slice, accepted decisions, and reproducible knowledge base. Local and cloud workspaces are disposable execution environments and do not outrank the GitHub repository.

Source precedence is: this contract and current ADRs; canonical foundation decisions and invariants; exact-stack runtime evidence; project dossiers and research; historical conversations and examples. Never silently merge a conflict; record the reconciliation and retain provenance.

Database-first rule: the reproducible knowledge base is the governing control plane for every task DiceBox Campaign Helper specializes in, as well as its pipelines and work routines. Before planning, creating, importing, compiling, adapting, or materially changing a JournalEntry or page, Actor, Item, Scene or map, Spatial Blueprint, Tile, Wall, door anchor, Region, RegionBehavior, Macro, teleport, puzzle, campaign package, module asset, adapter, harness routine, installation workflow, or recurring development procedure, query the approved read-only database surface and inspect applicable sources, facts, decisions, trials, open items, and schemas. Reuse an existing routine when possible. If a new routine is justified, record its purpose, authority boundary, owner, provenance, evidence receipt, failure/recovery behavior, and open risks in `database/seed.sql`, then rebuild and verify the database from `database/schema.sql` and `database/seed.sql`. A conflict blocks invention until explicitly reconciled; historical conversation and community examples cannot silently override the database.

General Codex/DiceBox AI rule for every chat: Codex repository work and the planned DiceBox Campaign Helper AI use the bounded loop `understand → consult → reconcile → plan → validate → preview → approve → execute → reread → recover → record`. Codex loads the instruction chain and read-only KB before specialized work, makes narrow reversible changes, verifies and reviews the diff, and reports evidence, blockers, and unknowns. The planned in-world AI classifies requests as explain, inspect, plan/preview, or execute/recover; treats model output and player requests as untrusted intent; requires current active-GM authority and exact runtime gates for mutation; uses versioned narrow adapters; rereads before commit; preserves unknown, foreign, and runtime-owned state; and emits blocker-based receipts. A player request, AI response, API existence, test pass, or successful transport response never grants Foundry authority or proves committed state. When this rule changes, active DiceBox Campaign Helper tasks receive a concise handoff message; the handoff does not override a more authoritative local contract or authorize live mutation.

Standing Campaign Helper development authorization rule: this applies to every current and future DiceBox Campaign Helper task/chat. The user grants standing permission to use any available tools and this machine for project-scoped development, code and document changes, testing, validation, local process and browser control, automation, runtime inspection, safe project-tool acquisition, and troubleshooting needed to complete the Campaign Helper roadmap/checklist. Ordinary in-scope work proceeds without repeatedly requesting the same approval, including bounded blocker diagnosis, environment repair, and recovery. Tool acquisition must remain project-relevant, use trustworthy sources, avoid unapproved spending or account commitments, and preserve rollback/provenance evidence. This permission does not waive platform policy or broaden the project target: resolve exact targets; preserve user and foreign state; prefer recoverable operations; protect secrets; reread outcome-unknown operations before retry; and retain the accepted-change, active-slice, database-first, destructive-action, external-publication/account/spending, and exact active-GM/Foundry gates. Player-role passwords remain blank and must not be generated, assigned, or persisted.

Mission and Foreman/Worker rule: the project mission and the normative single-Foreman, bounded-Worker, receipt, promotion, and clean-boundary handoff rules are defined in [docs/PROJECT-MISSION-AND-ORCHESTRATION.md](docs/PROJECT-MISSION-AND-ORCHESTRATION.md). Every task must either advance a named DiceBox deliverable, produce reusable evidence, or reduce a documented blocker. Workers do not create competing goals or authority; the Foreman reviews and records every result, and successful isolated work is reintegrated only after provenance, compatibility, authority, safety, and reproducibility review.

Model-routing and hidden-worker rule: for cleanly separable Campaign Helper work, the Foreman uses bounded internal Workers liberally whenever this advances a named deliverable without delaying the critical path, keeps their scopes disjoint, and closes them after Foreman receipt review. Route work according to the user-approved capability/efficiency chart: Luna Extra High for bounded implementation and evidence work; Luna High for routine implementation/tests; Luna Medium/Low only for clearly specified or mechanical work; Sol Medium for architecture and complex coding; Sol High for difficult debugging or migrations; Sol Extra High only for exceptionally hard problems or final review; Terra Extra High for broad repository exploration or an alternate reasoning pass; Terra High/Medium/Low only when that exploration fit is stronger. Do not silently substitute Luna Extra High where a different routed model is available and fits the assignment. Workers remain hidden internal actions rather than user-visible task threads, cannot create authority or auto-promote changes, and are closed rather than retained once their compact receipt is reviewed. If a platform offers no hidden/archive control, preserve the receipt and close the worker without creating a duplicate user-visible task.

Start from an identified source state; preserve user and foreign files; exclude shared live-runtime control unless separately authorized; return one compact receipt with source state, changed paths, provenance, validation, blockers, and recovery disposition; and require clean-boundary Foreman review before promotion. An isolated workspace cannot bypass the accepted-change synchronization gate, grant Foundry authority, auto-promote results, conceal or overwrite conflicting edits, or create a competing project goal. The roadmap, active card, shared idea document, reproducible KB, source repository, and runtime retain their existing authority.

Outcome-first efficiency rule: maintain one user-visible active outcome with a compact change card (acceptance observation, owner, target/authority, allowed scope, deterministic check, live check where needed, and stop/recovery condition). Keep at most one build, one live, and one research/recovery item active; park the rest of the ledger. Associate coordination rule: every collaborating Codex task that creates, changes, stages, installs, or binds a DiceBox-specialized asset must reproduce this contract in its own bounded workflow. Before producing map art, Spatial Blueprint, Scene, Tile, Wall, door anchor, Region, RegionBehavior, puzzle, Macro, adapter, or installer change, it must consult the helper knowledge base and consume the current versioned helper plan. Pixels, screenshots, and local defaults are never geometry authority. Map work follows `blueprint → walls/doors → empty renderer → Background Objects/Regions → runtime readback`; Background Objects are the workflow category for visible fixed environmental or puzzle apparatus after the renderer. `Foundry Tile`/`TileDocument` means the native Foundry document type and is reserved for an object that needs separate runtime positioning, visibility, movement, or state. Associates return the helper stable IDs, source version/hash, coordinate assumptions, exact Foundry APIs, preservation scope, and rereadable receipt; divergence is a blocker rather than a silent local adaptation.

Named DiceBox workflow contract rule: the user-facing workflow keywords `PREPARE → RENDER → INSPECT → APPROVE → BUILD` are versioned operations, not ordinary-language suggestions. For Foundry Scene Injector work, load and follow `.codex/skills/dicebox-injector-workflow/SKILL.md` and its referenced canonical sources before acting. A successful `BUILD` has exactly one primary deliverable: one Markdown (`.md`) file containing exactly one self-contained executable JavaScript injection macro. Embedded artwork may be compressed/chunked only inside that same macro and reassembled there; never require multiple user-run macros. ZIPs, loose package folders, multi-macro sequences, or improvised substitute artifacts are invalid. Before delivery, the artifact must pass `node tools/validate-dicebox-build.mjs <artifact.md>`. If the workflow, approved scene state, or validator cannot be loaded/reconciled, stop as BLOCKED rather than substituting another format. The 2026-10-05 ZIP regression is a permanent fail-closed test case documented in [docs/DICEBOX-INJECTOR-WORKFLOW-HARDENING-2026-10-05.md](docs/DICEBOX-INJECTOR-WORKFLOW-HARDENING-2026-10-05.md).

DiceBox map/token scale rule: all new generated battle-map Scene Injector work defaults to the versioned `battlemap-120` profile in [docs/DICEBOX-MAP-TOKEN-SCALE-STANDARD-2026-10-05.md](docs/DICEBOX-MAP-TOKEN-SCALE-STANDARD-2026-10-05.md). PREPARE must lock logical map dimensions before BUILD. Unless PREPARE contains an explicit user-approved exception, Scenes are Gridless with a 120px logical grid size, 5 ft distance, and pixel dimensions computed exactly as logical columns/rows × 120. Do not use 50px merely because a Scene is Gridless, do not use padding to repair scale, and do not resize token footprints or Token Scale Ratio to compensate for a map-scale mismatch. D&D5e token footprint remains system/Actor-size-owned; Scale Ratio is visual-only. New BUILDs must use `dicebox-scene-injector-build/v2`, define one `DICEBOX_SCENE_SCALE` source of truth, and pass the deterministic BUILD validator. L1-01 through L1-03 are legacy v1 scale artifacts and may be deliberately migrated, but must not be silently mutated.

DiceBox exploration discovery rule: Discovery Regions must be sparse, visually supported, and tied to plausible map features rather than functioning as invisible loot buttons. Ordinary maps default to 0–1 discovery and cap at 2 unless the user explicitly approves a discovery-dense special scene. The earlier pattern of roughly 60 discoveries across about 15 maps is rejected as too dense. Stage 1 is a flat d20 notice check with no modifiers against rarity/value DCs (Common 6, Uncommon 8, Rare 12, Very Rare 14, Legendary 16); failure is silent. Success reveals a private environmental hint and a suggested Stage 2 skill; it does not grant the item. Stage 2 uses an appropriate skill such as Investigation, Nature, Survival, Arcana, History, Religion, or Medicine. Stage 3 handles physical recovery separately. Hints should correspond to something visible or environmentally plausible on the approved renderer, but placement is not pixel-perfect: the visual clue and Region only need to be in a sensible nearby location that preserves the fiction. If no plausible visible anchor exists, revise the art, move the discovery to another sensible feature, or remove it rather than installing an arbitrary invisible Region.

Bounded GM operation transport rule: fixed, versioned, reviewed injection macros are the primary transport for DiceBox GM inspect, status, troubleshoot, and correct operations when an existing native adapter does not provide a dedicated status or control surface. They must be package-owned, exact-target and current-active-GM gated, strictly allowlisted, and free of arbitrary eval, `new Function`, raw sockets, or other unrestricted execution. Every operation is scope-bound; any write requires preview and approval, followed by an authoritative reread and blocker-based receipt. Injection macros preserve unknown and foreign state, never replace native/declarative mechanics, and use player ownership only when an explicitly player-facing macro is required. Existing macros may be used for read-only status to avoid unnecessary Foundry UI navigation.

M0 preserves these rules:

- Stable DiceBox IDs are canonical; Foundry IDs, UUIDs, names, and paths are runtime bindings.
- Native/declarative primitives are preferred and each mechanic has one owner.
- Utility and Use remain separate semantic categories.
- Spatial Blueprint owns geometry; images are renderers.
- Runtime state is sovereign during play.
- AI output is untrusted intent until deterministic validation.
- Player requests do not confer authority; the active authorized GM/executor rechecks authority and current state.
- Unknown or foreign state is preserved.
- No raw database edits, eval, `new Function`, arbitrary sockets, public execute-as-GM APIs, or hidden cleanup.
- Timeout is outcome-unknown; reread before retry.
- Ready-to-Play is blocker-based evidence, not a test percentage.

Do not implement broad mutation or campaign compilation until the M0 gate is reviewed.
