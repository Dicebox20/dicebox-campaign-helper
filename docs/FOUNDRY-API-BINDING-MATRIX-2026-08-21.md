# Foundry VTT API Binding Matrix

This is the API authority for DiceBox development plans. DiceBox semantic IDs, plan schemas, approval tokens, transaction journals, and evidence receipts are program-owned contracts. Any runtime operation that touches Foundry must use the corresponding versioned Foundry API below; a custom convenience API, raw database edit, arbitrary patch, or macro is not an acceptable substitute.

Target: Foundry VTT **14.367** and D&D5e **5.3.3**. The official API pages are v14 references and still require exact-target runtime verification before capability promotion.

## Hidden Region policy correction (accepted 2026-10-15)

**The blanket rule "hidden=true disables RegionBehaviors" is retired.** Do not reject or automatically unhide a functional Region based on that historical assumption. The user reports that a recent update corrected this limitation. A hidden Region is a valid design candidate. Before claiming gameplay functionality, verify the exact Foundry version, game system, modules, Region enabled state, event delivery, user permissions, active-GM boundary, and authoritative reread after reload.

This correction is user-accepted policy, not an independently verified live compatibility result. Earlier dated world observations remain historical evidence and must not be generalized to the current runtime.

## Binding rules

1. Every implementation-plan item that can affect a world must name its Foundry API, lifecycle boundary, capability ID, authority check, read-back API, and receipt evidence.
2. Use Foundry factory/document/collection APIs, never constructors as persistence and never raw database or LevelDB edits. Foundry documents explicitly document factory creation such as `JournalEntry.create` and schema validation.
3. Keep DiceBox IDs canonical. Foundry `_id`, `uuid`, names, paths, and flags are runtime bindings or projections; flags may carry an explicit DiceBox ownership marker only when the exact adapter contract permits it.
4. Treat API existence as static evidence only. The exact runtime probe and fixture must establish behavior, permissions, active-GM routing, and recovery.
5. Use the narrowest native API for the operation. Do not expose generic `Document.update`, arbitrary `createDocuments`, arbitrary sockets, or public execute-as-GM helpers through the DiceBox API.

## M3 managed JournalEntry slice

The semantic `ManagedJournalEntrySpec` is intentionally runtime-neutral. The exact adapter maps it to Foundry’s native JournalEntry shape:

```text
DiceBox title   → JournalEntry data.name
DiceBox content → JournalEntryPage data.text.content
page type       → CONFIG.JournalEntryPage.defaultType / exact runtime type
text format     → CONST.JOURNAL_ENTRY_PAGE_FORMATS.* observed on the target runtime
```

| Operation | Foundry API | DiceBox control |
| --- | --- | --- |
| Read known binding | `fromUuid(uuid)` or `game.journal.get(_id)` | Exact binding only; verify semantic ownership and generation |
| Read managed JournalEntry (separate adapter) | `fromUuid(uuid)` or `game.journal.get(_id)` | Read-only adapter accepts no factory/update/page-write dependency; verify the exact DiceBox marker and managed embedded page; resolution uncertainty is `UNKNOWN_OUTCOME` |
| Create parent | `JournalEntry.create(data, options)` | Active GM, approval token, idempotency key, bounded `name`/`pages` data |
| Create page | `entry.createEmbeddedDocuments("JournalEntryPage", data, operation)` when not created with the parent | Staged only when the parent binding exists; page schema from `CONFIG.JournalEntryPage` |
| Update parent | `entry.update(changed, options)` | Allowlisted fields only; expected generation and authoritative reread |
| Update page | `page.update(changed, options)` or parent embedded update API | Only the reviewed page binding; no arbitrary patch |
| Observe lifecycle | `preCreateJournalEntry`, `createJournalEntry`, `preUpdateJournalEntry`, `updateJournalEntry` | Diagnostics/receipts only after exact fixture proves hook order and payload |
| Present to users | `game.journal.show(entry, {users})` | Separate presentation operation; not a mutation authority |

The adapter-independent executor rechecks the current runtime profile and active-GM identity immediately before `JournalEntry.create`; it marks the transaction committed only after reading the returned binding through `fromUuid` or `game.journal.get` and matching the reviewed semantic record. A create result without a matching read-back remains outcome-unknown.

The bounded adapter uses the namespaced parent flag `flags["dicebox-campaign-helper"]` with exactly `schemaVersion`, `semanticId`, and `planId`. It verifies that marker before treating a document as DiceBox-owned; a missing or mismatched marker is foreign state and cannot be updated. The returned runtime binding includes the embedded `JournalEntryPage` id, so `JournalEntry.update(changed)` can preserve unrelated pages while changing only the reviewed managed page. A missing page binding, malformed page collection, or failed update read-back remains forbidden or outcome-unknown; it is never silently repaired.

The first live adapter must prefer creating the parent with its reviewed embedded page data in one native `JournalEntry.create` operation if the exact target schema accepts it. If the runtime requires staged page creation, the transaction journal must persist the parent binding before calling `createEmbeddedDocuments`. No plan may assume either shape without the exact 14.367 probe.

## Fixed-operation developer bridge

The local/loopback bridge is a bounded orchestration layer, not a replacement for Foundry APIs. Its operation contract is:

| Bridge operation | Foundry API relationship | Required gate |
| --- | --- | --- |
| `status` | Read-only runtime profile from the module probe; no Document API | Exact world ID and schema validation; always read-only |
| `fixture.select` | Harness-side fixture selection; no world mutation | Reviewed fixture ID, request ID, idempotency key |
| `plan.preview` | No Foundry mutation; previews the later `JournalEntry.create`/`update` plan | Exact runtime profile, capability findings, authority input, deterministic receipt |
| `snapshot.redacted` | `fromUuid`, `game.journal.get`, `game.journal.contents`, and bounded collection reads | Owned JournalEntry bindings only; hash runtime IDs; never emit title/content/raw `game` |
| `plan.applyApproved` | Later `JournalEntry.create`/`entry.createEmbeddedDocuments`/`JournalEntry.update` | Approval token, exact plan/receipt/GM identity, transaction journal, current runtime recheck; disabled by default |
| `reset.owned` | Later native JournalEntry read/update/delete only if exact reset contract permits it | Owned marker, active GM, explicit approval, reread, bounded fixture; disabled by default |

Unknown operation names, wrong worlds, reused idempotency keys with changed payloads, foreign bindings, and malformed snapshots are rejected before dispatch. The bridge must never expose arbitrary Foundry objects, macro text, raw database state, or public execute-as-GM behavior.

The bounded JSON-lines adapter is only a framing and response-validation seam for the fixed bridge. It does not create a Foundry capability or replace a Foundry API. Once an operation is admitted to an exact-runtime adapter, the adapter must still call the named Foundry surface in this matrix—such as `game.settings.get/set` for the gated journal or `JournalEntry.create`, `entry.createEmbeddedDocuments`, `JournalEntry.update`, and `fromUuid`/`game.journal.get` for managed documents—and must emit the corresponding runtime read-back receipt.

## Plan audit rule

Before a plan is considered implementable, review it against this matrix. A plan row that names only a DiceBox abstraction, a module name, a macro, an MCP tool, or a test command is incomplete until it also identifies the corresponding Foundry API and exact runtime evidence needed. The matrix is a design constraint, not a claim that any listed API is currently safe or available in the target world.

The program-side JSON-lines transaction store is an engine persistence implementation, not a Foundry API substitute. A module-side journal/settings/world-flag persistence choice must be separately named, capability-gated, and verified in the exact target world before it is used for live transaction recovery.
