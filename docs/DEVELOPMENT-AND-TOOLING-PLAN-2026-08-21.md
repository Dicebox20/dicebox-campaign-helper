# DiceBox Campaign Helper: Development, Implementation, and Harness Plan

Status: implementation plan and tooling contract for M0 review. This document does not certify a live Foundry world.

Foundry-facing plan items are governed by the [Foundry API Binding Matrix](FOUNDRY-API-BINDING-MATRIX-2026-08-21.md). Each runtime step must name its official Foundry API, lifecycle hook, capability gate, authority check, read-back path, and receipt evidence before implementation.

## Outcome and governing gates

The program and Foundry module share one semantic core. The program owns canonical DiceBox IDs, campaign truth, spatial blueprints, compiler plans, provenance, and receipts. The Foundry module is a versioned runtime adapter and projection executor. Foundry IDs, UUIDs, names, paths, and generated media remain runtime bindings.

Every capability moves through the same evidence ladder:

1. Contract: typed schema, ownership, authority, and forbidden-surface tests.
2. Static: package identity, syntax, dependency and source-boundary checks.
3. Deterministic: fixture tests, golden plans, redacted receipts, and database integrity.
4. Isolated browser: Utility Harness/Playwright behavior and accessibility evidence.
5. Visible browser: real Chrome with exact GM and Player3 contexts, console evidence, and screenshots.
6. Exact runtime: Foundry 14.367 + D&D5e 5.3.3 disposable-world behavior, read-back, retry/recovery, and sovereignty checks.

Ready-to-Play is blocked by any missing required lane; a green unit-test percentage is not a release certificate.

## Research transfer from Region Editor

Adopt the Region Editor patterns as adapters, not as permission to copy its implementation:

- Utility Harness Playwright configuration: one worker, stable base URL, HTML report, trace/screenshot/video on failure, and a dedicated `UTILITY_HARNESS_URL`.
- Accessibility checks through `@axe-core/playwright` for prompt and control surfaces.
- Two-context tests for GM and Player3, with explicit acknowledgment that isolated browser contexts cannot fully prove Foundry socket delivery.
- Locator/UUID equality checks, canvas prompt coverage, native Region write/read/reset checks, and a dedicated cross-scene teleport runner.
- Disposable fixtures whose cleanup can only remove artifacts tagged as owned by the current run.
- Rebuild/package checks before a live run; source tests are not live certification.

The local search did not find a separately named “Chrome Harness” repository. The evidence-bearing Chrome lane is the visible-browser flow: a real Chrome session with GM and Player3 Foundry tabs, exact build/module fingerprints, console/runtime diagnostics, and operator-visible screenshots. It is represented explicitly in `tools/harness-manifest.json` instead of being conflated with isolated Playwright.

## Research transfer from Dungeon Master’s Forge

Adopt these Forge testing patterns:

- Review-first lifecycle: preview a plan, produce review notes, require an approval token, then apply only that approved plan.
- Golden fixtures and generated-output contracts for compiler stability.
- Immutable diagnostic records with dated filenames; never overwrite a failed receipt.
- Redacted snapshots and prompt/provider hygiene; secrets, raw private prompts, and arbitrary macro source do not enter receipts.
- Explicit result taxonomy: `PASS`, `PARTIAL`, `MANUAL`, `FAIL`, `NOT TESTED`.
- A tester-only macro executor may exist only as a separately enabled exact-world fixture; it is not a general execution path.
- A loopback MCP bridge may expose fixed operations only: status, fixture selection, safe preview, approved apply, redacted snapshot, and reset of Forge-owned/DiceBox-owned fixtures.

Reject or constrain: arbitrary JavaScript, arbitrary macro execution, fuzzy document search, raw database edits, public execute-as-GM APIs, automatic retries, and reset of campaign-owned or foreign state.

## Harness architecture

The repository now has a machine-readable harness manifest and `npm run verify:tooling`. They are intentionally dependency-light and verify the useful boundary before a live harness is installed.

| Lane | Best use | Cannot prove |
| --- | --- | --- |
| Contract/Vitest | Pure core, adapters, schemas, compiler plans | Foundry behavior |
| Static/package verifier | Manifest identity, ESM syntax, forbidden surface, KB integrity | Runtime import |
| Utility Harness/Playwright | DOM, prompt flow, accessibility, screenshots, two isolated clients | Real socket routing and world persistence |
| Visible Chrome | Real rendering, console, two user sessions, operator evidence | Repeatable unattended certification by itself |
| MCP loopback | Deterministic fixture orchestration and redacted state reads | Campaign-world safety or manual proof |
| Exact Foundry | Documents, permissions, active GM, Regions, Activities, recovery | Nothing outside its frozen fingerprint |

For Playwright, use projects to separate setup, GM, Player3, accessibility, and cross-scene suites; use trace and HTML reports as evidence artifacts. Keep retries bounded: a timeout is outcome-unknown, so re-read before retrying. Use Vitest projects later when core, bridge, and browser-facing tests need separate environments. Coverage is a diagnostic, not a readiness gate.

## MCP server expansion

MCP is useful as a typed evidence and orchestration boundary, not as a tunnel for arbitrary Foundry code. MCP servers expose distinct resources, prompts, and tools; their control surfaces should remain separate:

- Resources: KB slices, target fingerprints, capability snapshots, fixture definitions, prior redacted receipts, and current blocker reports. The host/application decides when these are supplied.
- Prompts: review checklists, preview/apply workflows, failure-injection recipes, and release evidence templates. Keep prompts user-controlled and versioned.
- Tools: fixed, schema-validated operations such as `dbx_test_status`, `dbx_fixture_select`, `dbx_plan_preview`, `dbx_plan_applyApproved`, `dbx_snapshot_redacted`, and `dbx_reset_owned`. Tools must require exact world, active GM, request ID, idempotency key, and approval token where mutation is involved.

Recommended deployment order:

1. Local stdio MCP server for deterministic core/KB queries.
2. Foundry-side developer bridge on `127.0.0.1` for the exact disposable test world.
3. Optional remote MCP only through an authenticated, consented tunnel with read-only tool filtering by default.

The bridge must enforce loopback origin, one connected Foundry world, exact world ID `dbx-test-world`, GM presence, fixed operation allowlists, bounded JSON-lines payloads, strict response envelopes, redaction, timeout-unknown handling, and owned-fixture reset. It must never expose raw `game`, arbitrary document mutation, macro text, provider secrets, or a general execute-as-GM primitive. The current Codex session exposes generic MCP connectors but no configured DiceBox/DMF bridge server, so the repository now contains a transport-neutral JSON-lines seam rather than pretending the bridge is live.
